# Étape 3 — v0.22-dev, corrections après revue indépendante

La v0.21-dev a été revue par Antigravity sur l'archive de SHA-256 `f601d9c894dd816fd9ebe744427693f19ec7a8c3ba1d24e9bac4d8ed44923c31`. L'utilisateur a confirmé sur Ubuntu 228 tests standard sans skip, un ex00 local sous cgroup réel et un parcours HTTPS GitHub + Bubblewrap + cgroup sur le commit `cc5e12c0776839a33ef12658192a0f46abdcf095`. Ces essais sont des résultats **v0.21**, pas une validation de la v0.22. La v0.22 n'est pas encore revue indépendamment ni éprouvée en scope réel dans l'environnement de développement. Code et dépôts de confiance uniquement ; sécurité non terminée.

Le témoin OOM et le témoin CPU associés restent désactivés, y compris avec `ML_TEST_CGROUP_LOAD=1`. **Ne jamais lancer l'ancien témoin OOM de la v0.20 sur la session utilisateur.** Aucun OOM ni essai de saturation n'a été lancé pour la v0.22. Les limites `memory.max` et `cpu.max` ne sont pas validées en charge ; une méthodologie distincte revue et une VM jetable sont nécessaires.

## Analyse des sept constats

**V21-01 — signaux, interruptions et nettoyages.** Le worker cgroup utilise désormais les gestionnaires temporaires SIGTERM/SIGHUP pendant `serve` ; une interruption déroule les contextes Python, puis il tente une réponse indisponible. La CLI utilise ces gestionnaires et convertit une interruption pendant l'acquisition ou l'évaluation en rapport `incomplete`, en conservant le diagnostic de capture s'il existe. Le lanceur préserve les messages d'erreur précédents lorsqu'un nettoyage reste incertain. Tests par sous-processus : SIGTERM en cours de correction CLI et de worker simulé ; dossier temporaire nettoyé dans ces scénarios. Un autre test interrompt une vraie capture de processus de confiance et confirme sa fin et le nettoyage du dossier. **Pas de scope systemd réel dans ces tests.** Le scope peut déjà être en cours d'arrêt et le message du worker peut ne pas parvenir au lanceur. Une interruption ailleurs dans la CLI ou dans une fenêtre critique, un deuxième signal, SIGKILL, les threads, un processus détaché ou bloqué peuvent toujours empêcher un nettoyage ou un rapport. Aucune garantie générale.

**V21-02 — noms non UTF-8.** Reproduction sur la v0.21 : un nom local contenant l'octet `FF` produit une sortie JSON non UTF-8 et empêche l'historique de s'enregistrer ; dans cet essai particulier, `UnicodeEncodeError` était interceptée comme `ValueError` par la CLI et ne causait pas le traceback prédit, puis la CLI renvoyait le code d'échec du rendu. Le comportement d'affichage dépend du flux et de sa configuration. La v0.22 refuse les noms Git et sous-dossiers Git contenant des surrogates, et échappe les surrogates dans les diagnostics locaux et l'étiquette d'historique sans altérer les caractères UTF-8 valides. Cela ne constitue pas une validation générale de toutes les données entrantes.

**V21-03 — auxiliaires SQLite.** Contrôles statiques des fichiers existants `-journal`, `-wal`, `-shm` : seul un fichier régulier à lien unique est accepté ; aucun lien n'est supprimé automatiquement. Reproduction isolée avec la v0.21 et SQLite 3.46.1 : un `-wal` préexistant sous forme de lien physique vers un fichier témoin a vu son contenu modifié pendant `store_attempt`. Avec cette même bibliothèque, les liens symboliques `-journal` et `-wal` essayés ont été refusés, et non suivis ; il serait incorrect de généraliser l'affirmation inverse à toutes les versions/configurations SQLite. Les nouveaux contrôles restent séparés de l'ouverture SQLite : ils n'éliminent pas les courses ni ne protègent d'un autre processus du même UID. Les permissions des données préexistantes ne sont pas corrigées.

**V21-04 — dashboard.** Si `os.fdopen` échoue, le descripteur est fermé et le fichier temporaire est supprimé ; testé avec erreur simulée. D'autres fenêtres d'interruption existent, notamment entre `mkstemp` et le bloc de nettoyage. La vérification statique du lien destination ne supprime pas la course avant `os.replace` ; celui-ci remplace le lien final, il ne suit pas sa cible. Les dossiers parents ne sont pas protégés contre un adversaire même UID.

**V21-05 — rapport favorable.** Seuls les contrôles `pass` prévus et les noms `info` connus sont acceptés ; seuls les avertissements `Sortie stderr` peuvent se répéter. Les neuf exemples réels C00 ont été évalués en Bubblewrap et leurs rapports favorables acceptés par le validateur. Un protocole futur ajoutant un nouveau contrôle doit aussi mettre à jour cette liste. Les contrôles de structure ne prouvent pas l'authenticité du rapport face au même UID.

**V21-06 — sorties de compilation.** En échec ou exception, une sortie précréée est supprimée si son identité et son type correspondent encore ; un fichier remplacé n'est pas intentionnellement supprimé et l'incertitude est remontée. Son descripteur reste ouvert pendant l'opération afin de conserver l'inode initial. Des tests couvrent échec, exception et remplacement. Ce contrôle reste séparé de `unlink` : une course même UID demeure. SIGKILL peut laisser le dossier de travail temporaire ; le nettoyage reste de meilleure intention.

**V21-07 — sonde et documentation.** Une invocation directe de `python -m moulinette.cgroup_load_probe` affiche `unavailable` puis retourne 2, sans charge ; le test réel associé demeure sauté inconditionnellement. Le compteur de tests de la documentation active a été actualisé.

## Limites qui demeurent

GitHub partage le réseau, s'exécute hors du cgroup de correction et dispose d'un tmpfs borné qui n'est pas un quota global. Ni seccomp, ni isolation forte vis-à-vis du même UID, ni protection contre le noyau partagé et les descendants détachés ne sont démontrés. L'interruption brutale et les courses de chemins restent ouvertes. Aucun mode n'est adapté au code ou dépôt hostile. Voir `validation-v0.22-dev.md` pour les essais effectués et `prompt-audit-v0.22-dev.md` pour la prochaine revue.
